# Virtua Tennis hardware and fixed-translation feasibility

Investigated on 2026-09-23. No game has been built or run by this investigation. The existing Model 1/2 translation architecture is reusable as a method, but its CPU generators and hardware are not a direct NAOMI implementation.

## Hardware baseline

The prior pinned MAME source is commit `ae30b778caef8d7f9fdd45da7ac88fa42596427e`. Its `vtennis` registration uses the NAOMI M2 cartridge configuration and is marked not working with imperfect graphics and sound. The driver explicitly identifies incomplete PowerVR/AICA features and performance as reasons for withholding working status. The linked author's QA records Virtua Tennis crashing after the Sega logo and before gameplay, but that document is dated January 2022; it is historical evidence, not a fresh execution result. Fixed CPU/reference parity would reproduce hardware defects and would not itself demonstrate playability. [Pinned MAME driver](https://github.com/mamedev/mame/blob/ae30b778caef8d7f9fdd45da7ac88fa42596427e/src/mame/sega/naomi.cpp), [author's historical QA](https://github.com/angelosa/mame_qa/blob/main/mame_qa/naomi.md).

The MAME configuration includes an SH7091 SH4, AICA ARM7, programmable AICA DSP, MIE Z80 and an instantiated TMP90PH44 JVS-board CPU. Its communication-board M68000 starts held in reset. A live device/PC inventory would be needed to distinguish actually executing auxiliary devices from simulated or parked ones. The main address map contains a 2 MiB BIOS, 32 MiB main RAM at `0x0c000000–0x0dffffff` with aliases, 8 MiB sound RAM and PowerVR command/texture/framebuffer interfaces. Sound code is loaded into RAM shared by SH4 and ARM7. The AICA DSP executes writable program words, so it also requires fixed program-image support rather than retaining its decoder.

The more practical candidate is **Flycast**, pinned to `628bd3dbb160ea2750230fc6b00c0bb8173cb1f6`. It has maintained NAOMI hardware/rendering support, a macOS frontend and the exact `vtennis` cartridge definition. This is a feasibility basis, not a claim that this port already runs. It offers OpenGL and Vulkan renderers. Its MIE/JVS implementation handles board messages and firmware uploads in native protocol code; it does not execute a Z80 or JVS MCU. Keeping that existing abstraction leaves three programmable execution engines to replace: **SH4, ARM7 and AICA DSP**. It must be described as simulated I/O hardware, not fixed translation of those unexecuted MCU firmwares. [Pinned Flycast source](https://github.com/flyinghead/flycast/tree/628bd3dbb160ea2750230fc6b00c0bb8173cb1f6), [cartridge definition](https://github.com/flyinghead/flycast/blob/628bd3dbb160ea2750230fc6b00c0bb8173cb1f6/core/hw/naomi/naomi_roms.cpp), [MIE/JVS protocol implementation](https://github.com/flyinghead/flycast/blob/628bd3dbb160ea2750230fc6b00c0bb8173cb1f6/core/hw/maple/maple_jvs.cpp).

## Verified initial code images

The supplied `epr-22927.ic22` is 4,194,304 bytes, CRC32 `89781723`, SHA-256 `aac8608949d7539465459bca990fa21dfb0406be02e77fdc721dd266c482e132`. Its unencrypted boot header was parsed using the pinned `RomBootID` layout; no media was modified.

| Mode | Cartridge source | Destination RAM | Initial PC |
| --- | --- | --- | --- |
| Game | `0x000000–0x3fffff` | `0x0c020000–0x0c41ffff` | `0x0c021000` |
| Game test | `0x300000–0x3fffff` | `0x0c020000–0x0c11ffff` | `0x0c020000` |

These are overlapping executable-image addresses, not immutable low-address cartridge execution. The SH4 BIOS resets at `0xa0000000`; cached/uncached aliases and translated addresses must preserve the original virtual PC. Later code uploads, overlays or self-modifying instructions remain **unmeasured**. Flycast supports code invalidation generally, but that does not prove this particular game modifies instructions.

Both primary core definitions identify the cartridge as M2 with key `0x2803eb15`. This is cartridge-board cryptography, not an SH4 instruction cipher. Retain the existing board state/decryption behavior and derive fixed executable images from verified media and original observed uploads. A cartridge header being readable does not mean every later board read is unencrypted. [Boot-header layout](https://github.com/flyinghead/flycast/blob/628bd3dbb160ea2750230fc6b00c0bb8173cb1f6/core/hw/naomi/naomi_cart.h).

## Implementable fixed execution boundaries

- **SH4:** replace the opcode-table dispatch in `core/hw/sh4/interpr/sh4_interpreter.cpp` with guarded fixed-address entries. Generate constant-specialized bodies from `sh4_opcodes.cpp` and `sh4_fpu.cpp`. Also specialize FPU classification and `Sh4Cycles::countCycles`; retaining `OpPtr[opcode]`, `OpDesc[opcode]`, or opcode-driven cycle classification in shipping code would violate the architecture. Cover Run, Step, ordinary delay slots and the special RTE delay-slot SR ordering. Preserve the original exception handling, FPU state/rounding, MMU, instruction/data caches, store queues, DMA and scheduling.
- **Instruction identity:** observe each original instruction fetch once, recording virtual PC and the returned word. Runtime native fetches may authenticate a known entry, but must not decode it. Compare against the instruction-cache-visible word, not an arbitrary raw-RAM peek: stale I-cache data can legitimately differ from writable RAM. Multiple known words/images at a PC require authenticated fixed variants. Unknown execution must fail closed.
- **ARM7:** `core/hw/arm7/arm7.cpp` includes `arm-new.h` inside its interpreter loop. The header already supports `NO_OPCODE_READ`, which provides a useful offline-constant specialization boundary. Preserve conditional execution, banked registers, interrupts, pipeline PC and cycle increments. Obtain the real sound-driver image(s) and any reload variants from original execution. No ARM recompiler or arbitrary instruction switch can remain linked into the native build.
- **AICA DSP:** specialize all 128 DSP steps from verified uploaded program images. Retain sample timing, accumulator precision, memory pipeline and original zero-instruction behavior. Authenticate complete program images, including transient reload states if they execute; mutable audio coefficients and sample RAM are data. The existing runtime DSP interpreter and JIT must be absent from shipping linkage.

The supported `TARGET_NO_REC` build switch selects `DYNAREC_NONE` for `FEAT_SHREC`, `FEAT_AREC` and `FEAT_DSPREC`. `DYNAREC_NONE` is `0x40000001`, not numeric zero. This only selects the original interpreters: it is appropriate for the isolated oracle, but is **not** fixed native translation. The final source/link audit must also exclude those original interpreter bodies, all recompiler backends and fallback factories. Normal graphics-driver shader compilation is unrelated to emulated CPU instruction translation.

## Bounded proof before committing to the port

1. Build an unchanged interpreter-only Flycast reference. With the supplied BIOS/cartridge and deterministic saved settings, reach attract, player selection and an actual playable match. Inspect court/net/ball/player visibility, controls and sound. If that original baseline is unusable, stop before treating CPU parity as success.
2. Build an isolated observer from a derived source copy. Capture unique SH4 virtual-PC/word pairs, ARM PC/word pairs, DSP image changes and the original code uploads. Pin the media, source revision and all observation changes. Require observer/reference gameplay, CPU-state and audio equality where deterministic; GPU presentation needs a documented comparison method if raster output varies.
3. First replace one CPU family at a time. Use synthetic semantic fixtures for delay slots, RTE, exceptions, FPU modes, cache/MMU behavior and sound interrupts, plus exact original-input hybrid comparisons. The BIOS, normal-game and game-test loading paths are separate required cases.
4. Only then integrate all three fixed engines, remove decode/JIT fallback linkage and extend actual-input coverage through serves, rallies, scores, games, match endings, continues, service exits and fresh-session/reset behavior. Performance must be measured with the real renderer and audio pipeline.
